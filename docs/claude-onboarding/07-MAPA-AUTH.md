## 3. `useAuth` (`src/hooks/useAuth.ts`, 151 LOC, 19 importadores)

Estado:
```ts
{ user, session, userId, isAuthenticated, isLoading, isPasswordRecovery }
```

Mecânica:
- `supabase.auth.onAuthStateChange` — **ignora eventos repetidos para o mesmo usuário** (`TOKEN_REFRESHED`, `SIGNED_IN`, `INITIAL_SESSION`, `USER_UPDATED` quando `newUserId === currentUserId.current`), evitando re-render em massa.
- Revalidação em `visibilitychange` / `focus` / `pageshow`, com throttle de **30 s** (`MIN_FOCUS_CHECK_INTERVAL`); só faz `getSession()`, sem refresh manual.
- Detecção de recuperação de senha: `window.location.pathname === '/reset-password'` **E** hash contém `type=recovery` + `access_token`.

**`isPasswordRecovery` abre uma porta no guard**:
```tsx
// SimpleAuthGuard
if (isAuthenticated || isPasswordRecovery) return <>{children}</>;
```
Como `isPasswordRecovery` é derivado do hash da URL, uma navegação para `/reset-password#type=recovery&access_token=...` satisfaz o `SimpleAuthGuard`. Na prática o Supabase valida o token ao chamar `updateUser`, e todas as rotas relevantes têm `SecureRouteGuard` acima; ainda assim é um caminho de renderização sem sessão validada.

## 4. Armazenamento da sessão — `previewAuthStorage.ts`

Arquivo gerado pelo Lovable ("This file is automatically generated. Do not edit it directly.").

Comportamento:
- Fora de zonas de preview → **`localStorage` padrão**.
- Em `lovableproject.com`, `lovableproject-dev.com`, `lovable.app`, `gpt-eng.com`, `gptengineer.run` **e dentro de iframe** → faz *brokering* da sessão via `postMessage` para o editor Lovable.

**Avaliação de segurança:** a implementação é defensiva e correta —
- extrai o `projectId` apenas de posições do host não controláveis pelo usuário (regex ancorada com UUID v4);
- valida a origem do editor contra `^https://([a-z0-9-]+\.)*(lovable\.dev|gptengineer\.app)$`;
- só responde a mensagens vindas dessas origens;
- timeout de 2 s.

Em produção (`lytotec.com.br`) esse caminho **não é ativado** — usa `localStorage`.

**Ponto a registrar:** enquanto esse arquivo existir, a aplicação em preview compartilha sessão com o editor Lovable. Se a transição para Claude Code eliminar o uso do preview Lovable, este arquivo torna-se legado — mas **não deve ser removido sem autorização** (é gerado e referenciado por `client.ts`).

## 5. Configuração de Auth no Supabase (documentada em `SUPABASE_AUTH_CONFIG.md`)

```
Site URL:            http://lytotec.com.br
Redirect URLs:       http://lytotec.com.br/reset-password
                     http://lytotec.com.br/*
                     http://localhost:3000  (+ /reset-password, /*)
```

⚠️ **Todas as URLs de produção estão em `http://`, não `https://`.** O documento diz "Quando HTTPS estiver disponível, adicionar também…", indicando que o HTTPS ainda não foi adotado. `VITE_APP_PUBLIC_URL` no `.env` confirma: `http://lytotec.com.br`.

**Implicação:** links de recuperação de senha e o próprio `access_token` no fragmento de URL trafegam por HTTP em claro. Classificado em `14-RISCOS-SEGURANCA.md` §2.

**`[VERIFICAR]`** — se o domínio já está atrás de HTTPS no Netlify (redirect automático), o risco cai substancialmente. Confirmar acessando `http://lytotec.com.br` e observando se há `301 → https`.

## 7. Autenticação secundária: dispositivos de Ponto

Fluxo **independente do Supabase Auth**:

```
PontoTotemLogin  →  Edge login-dispositivo-totem  (verify_jwt = false)
                     │  valida bd_ponto_dispositivos.codigo_dispositivo + senha_hash (bcrypt)
                     ▼
                    device_session_token  +  device_session_expires_at
                     ▼
Header x-device-secret nas Edges:
   identificar-funcionario-por-face · confirmar-match-totem · registrar-ponto-totem
```

Provisionamento (exige SuperAdm real via `is_super_admin`):
- `definir-senha-dispositivo` (bcrypt, mínimo 8 e máximo 128 caracteres)
- `vincular-ccs-dispositivo` (N:N `bd_ponto_dispositivo_centros_custo`, exige ≥1 CC)
- `heartbeat-dispositivo` (autenticado por `x-api-key` = `LYTOTEC_API_KEY`)

**Achado:** `login-dispositivo-totem` **não consome** `fn_rate_limit_check` nem `bd_rate_limit_tentativas`. Ver `14-RISCOS-SEGURANCA.md` §6.

## 8. Cache, offline e persistência

| Camada | Local | TTL | Assinado? |
|---|---|---|---|
| Sessão Supabase | `localStorage` (chave do supabase-js) | conforme JWT + refresh | JWT assinado ✔ |
| `_cache` de permissões | **variável de módulo** em `usePermission.ts` | 60 s | n/a (memória) |
| `user_offline_context` | `localStorage` | 24 h | **NÃO** ✘ |
| Fila offline de apontamentos | IndexedDB/localStorage (`src/utils/salvarOffline`) | — | — |
| Caches do Service Worker | `lyto-html-v2`, `lyto-assets-v2`, `lyto-images-v2` | — | — |

### 8.1 `user_offline_context` — objeto não assinado usado para autorização

`src/utils/offlinePermissions.ts` grava em `localStorage`:
```json
{ "userId": "...", "email": "...", "isSuperAdmin": true,
  "permissions": ["*"], "userRole": "SuperAdm",
  "validatedFromServer": true, "timestamp": "..." }
```
Validação na leitura: apenas **idade < 24 h** e (em `getValidatedOfflineContext`) `userId` correspondente + `validatedFromServer === true`.

**Não há assinatura, HMAC ou verificação server-side.** Consumidores:
- `usePermission.ts` Camada B → define `permissions = ['*']`
- `SecureRouteGuard` → `emergencyAdminBypass` → renderiza children direto
- `canAccessOfflineModule()` → libera módulos offline

### 8.2 Service Worker e auth
`public/sw.js` faz bypass explícito e correto de tudo que é sensível:
```js
if (url.hostname.endsWith('.supabase.co')) return true;   // nunca cacheia
if (url.pathname.startsWith('/functions/v1/')) return true;
if (url.pathname.startsWith('/auth/')) return true;
if (url.pathname === '/version.json') return true;
```
Nenhum token ou resposta de API é armazenado em cache. **Implementação correta.**

## 10. Consultas / verificações de diagnóstico

```sql
-- Usuários auth sem profile
select count(*) from auth.users u
where not exists (select 1 from public.profiles p where p.id = u.id);

-- Profiles sem usuário auth (órfãos)
select count(*) from public.profiles p
where not exists (select 1 from auth.users u where u.id = p.id);

-- Usuários sem e-mail confirmado
select count(*) from auth.users where email_confirmed_at is null;

-- Usuários "aguardando aprovação" (sem role e sem legado)
select count(*)
from public.profiles p
where not exists (select 1 from public.bd_user_roles ur where ur.user_id = p.id)
  and p.funcao_permissao is null
  and coalesce(cardinality(p.funcoes),0) = 0;

-- Dispositivos de ponto ativos e sessões vivas
select id, codigo_dispositivo, tipo, ativo,
       (senha_hash is not null) as tem_senha,
       device_session_expires_at
from public.bd_ponto_dispositivos
order by ativo desc, codigo_dispositivo;
```
